# わたしは、なに？

スマホ1台を回して遊ぶ、日本語の「自分のお題を当てる」ゲームです。人数を先に決め、ジャンルを選ぶと人数分の番号ボタンが出ます。その番号の本人だけ画面を見ず、他の人がお題を確認します。

- 2〜50人。食べ物・場所・もの・動物など24ジャンルと数字。
- 自動配布、全員同じジャンルのランダム、各自違うジャンルのランダム。25人を超える場合、ジャンルは一巡してから再利用します。お題は別々です。
- 順番に決めるモード：1番が2番、2番が3番…最後の人が1番のお題を決めます。入力の前後は受け渡し画面で隠します。
- 「知らない → お題をチェンジ」でその人だけのお題を変更。自動モードは同じジャンルの未出題のお題、手動モードは元の出題者が入力し直します。
- ゲーム終了は確認ダイアログ付き。最初の画面に戻っても出題履歴は残します。
- 表示中のお題は、別アプリに切り替えたときや再読み込み時に隠します。

## お題と重複防止

内蔵辞書は正規化後5,385語です。24ジャンルに属する1,919件（重複をまとめて1,907語）を身近なお題として優先し、使い切ると他の内蔵語、検索候補の順に使います。具体的な件数は `health.json` に記録します。

同じ表記・全半角・ひらがな／カタカナ違い・登録済みの別名をまとめ、今回と過去のお題を避けます。手入力でも重複は拒否します。チェンジ前のお題も履歴に残り、候補がなくなっても勝手に再出題しません。未登録の同義語までの意味判定、別ブラウザー間の共有はしません。履歴消去は明示した別操作です。端末のブラウザーデータ消去や保存できない設定では履歴を維持できません。

## 検索はチェックONのときだけ

初期値はOFFで、ゲーム中に外部へ問い合わせません。ONのときだけ日本語版Wikipediaの公開APIを使い、ページ名をお題候補にします。本文・画像・プレイヤー名・出題履歴を送受信しません。検索に使ったジャンルや検索語はWikipediaへ送られます。

「候補を補充」で、選んだジャンルの未使用候補を最大3,000件まで追加します。取得は直列、1回最大60秒で停止・続きから再開できます。実際に取得できた件数を表示し、存在しない語で水増ししません。各ジャンルに必ず数千語あるという意味ではありません。検索先の件数・接続・分類によって増やせない場合があります。検索OFFでは、取得済みのオンライン候補も出題しません。通信失敗時は内蔵語だけで遊べます。

## 開発・検証

Node.js 20以上、Python 3（確認用サーバー）、Chromium（ブラウザーテスト）が必要です。アプリ本番は単一HTMLの静的サイトで、サーバー処理やAPIキーは不要です。

```sh
npm ci --ignore-scripts
npm run build
npm test
npm run test:browser
npm start
```

ブラウザーテストは `CHROMIUM_PATH` または `/usr/bin/chromium` を使い、Wikipedia応答をローカルで模擬してON/OFF・3,000件・中止・失敗などを検証します。実サービスの可用性テストとは別です。

編集元は `kotoba-party/` です。`common-words.json` は身近な語の選定、`words-*.txt` は全辞書、`engine.js` は抽選・重複防止、`app.js` は画面・検索、`style.css` はスマホ表示です。`npm run build` が `kotoba-party/public/` とリポジトリ直下の `index.html` / `health.json` を生成します。公開HTMLに秘密情報は含めないでください。

## URL公開（GitHub Pages）

`index.html` と `.nojekyll` があるブランチのルートをGitHub Pagesの公開元に設定します。このリポジトリでは `main` と公開用 `gh-pages` のどちらも同じゲームを配布できる構成です。

公開用ブランチの更新：

```sh
bash scripts/publish-pages.sh
```

初回にGitHub側で公開元の指定が必要な場合は、リポジトリの Settings → Pages → Deploy from a branch → `gh-pages` / `(root)` → Save を選びます。

予定URLは `https://mateo-purple.github.io/any/` です。Pagesの公開設定・配信が完了した後に使用できます。ソースのpushやローカルでの動作確認だけでは公開確認にはなりません。
